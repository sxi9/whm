# HTTPS by default — what is on, where it lives, how to turn each part off

The owner's rule: everything the panel provisions serves HTTPS unless an operator turns it off.
This page lists each default, the setting or switch behind it and what turning it off does.
Nothing here needs a restart unless the row says so.

| Default | Where it is applied | Setting / switch | Off means |
|---|---|---|---|
| **Sites redirect HTTP to HTTPS once they have a certificate** | `web.vhost.write` renders a `mod_rewrite` block into the port-80 `<VirtualHost>` of every vhost whose spec carries `ssl` (`redirectHttps: true`). Direct Apache: `RewriteCond %{HTTPS} off`; behind the NGINX proxy (Apache bound to `127.0.0.1:<port>`): `RewriteCond %{HTTP:X-Forwarded-Proto} !=https`, since NGINX terminates TLS and forwards the scheme. `/.well-known/acme-challenge/` is excluded so renewals keep working. Vhosts without a certificate never redirect. | Setting `web.force_https` (default `true`). Service Configuration › Apache Configuration › *Redirect HTTP to HTTPS when a certificate is installed* saves it through `PUT /api/system/settings` and queues `POST /api/service-config/apache/vhosts/sync` so every vhost is re-rendered; `ctx.web.apache.setForceHttps(false, req)` does both in one call. | New renders leave the block out; the sync job rewrites existing vhosts. Requires `mod_rewrite` (the page warns when it is not loaded: `a2enmod rewrite`). |
| **The panel itself answers only on 2087** | `server/src/app.js`: when the panel has TLS (`tlsCert` + `tlsKey`), a request that arrived on the plain listener (`req.socket.encrypted` is false) gets `301 https://<host>:<tlsPort><path>`. `/api/health` and `/.well-known/acme-challenge/` stay on HTTP. The host header is echoed only when it is a bare hostname or IP literal. | Setting `panel.force_https` (default `true`, read per request). Overrides: `WHM_FORCE_HTTPS=false` in the environment or `forceHttps: false` in `whm.conf` (read by `app.js`; `config.js` does not list the key yet). | Port 2086 serves the panel over plain HTTP again. Session cookies stay `secure` while TLS is on, so logging in over 2086 does not work either way. |
| **The hostname gets its DNS records** | `networking.setHostname` (Networking Setup › Change Hostname) publishes through DNS Functions: the A record (`ensureHostnameA`, creating the parent zone when needed), AAAA when the server has a public IPv6 (`basic.main_ipv6`; loopback, link-local, ULA and v4-mapped addresses are skipped), `www.<hostname>` as a CNAME and an MX pointing at the host itself. One failing record is reported inside the `dns` step; the A record decides the step. | `addDnsRecord` on the request (service default `true`; the page seeds it from `networking.hostname.add_dns_record`, saved with *Save toggles as defaults*). | No records are touched. |
| **The hostname has a landing page** | `ctx.web.ensureHostnameVhost()` renders a `web_vhosts` row of type `server` (user = Apache's run user, docroot `/var/www/whm-default`, no PHP) for the hostname and writes `index.html` from the `landing` web template. Runs on `panel.started` (emitted by `server/src/index.js` once the listeners are up), on every hostname change (`landing` step), when the `landing` template is saved or reset (the save response carries `rendered: { hostname, applied, landingPage, reason, error }`) and in the *Re-render all* vhost job. The row is left out of the account vhost counts. A hostname that is a hosted domain, or not fully qualified, is refused (`hosted_domain` / `invalid_hostname`). | No switch: it exists whenever the hostname is valid. Edit the page under Account Functions › Web Template Editor (template `landing`, variables `{{company_name}} {{tagline}} {{logo_url}} {{panel_url}} {{domain}} {{hostname}}`). | Remove the row from the vhost list and set a non-FQDN hostname; or override the template with your own HTML. |
| **The hostname is never a hosted domain** | Both directions are enforced. `networking.setHostname` refuses a hosted domain (409, `hostedDomainConflict`); the vhost layer refuses the reverse: `ctx.web` throws 409 `conflict` from every path that stores or writes a vhost (`ensureVhost`, `addAlias`, `setAccountIpv6`, restores through `storeSpec`) when the domain or an alias is the hostname or `www.<hostname>` (`ctx.web.isServerName(domain)`), or when the stored row for that domain is the `server` row. An account's vhost spec only inherits a stored row (certificate, custom directives, IPv6, PHP version) that the same account wrote; another owner's row, the `server` row included, is treated as absent. Why: a tenant vhost for the hostname would answer `https://<hostname>/` with the hostname's certificate and receive the panel's host-only session cookie from the admin's browser. | None. Account, addon, parked and sub-domain creation must refuse the same names before a Linux user exists (`ctx.web.isServerName`). | — |
| **The hostname gets a certificate, installed everywhere** | `certificate` step of the hostname change and `POST /api/networking/hostname/certificate` (*Reissue hostname certificate*, root): when AutoSSL has a provider that is installed and the hostname resolves to the server's public IPv4, the certificate is issued through `ctx.ssl.issueFor` (falls back to the AutoSSL issuer with a synthetic `server` row because the hostname is never a hosted domain), then installed with `ctx.ssl.installServiceCert` for `panel`, `exim`, `dovecot`, `ftp`; the hostname vhost receives it through the issuer's web hook. The step reports `installed`, `failed` and `pending`: `panel` is only *installed* when the pair the agent wrote (`result.applied`) is the pair the listener reads (`config.tlsCert`/`tlsKey`, i.e. `whm.conf` or `WHM_TLS_CERT`/`WHM_TLS_KEY`); a pair written elsewhere, or a panel without a TLS listener, is *pending* with the agent's note and the step is not `ok` (`code: not_live`). The panel's TLS listener polls its configured files every 30 s (`watchTlsFiles` in `server/src/index.js`) and swaps the pair in without a restart once they change. **Renewal:** AutoSSL's run only visits hosted domains, so the job `networking.hostname.certificate` (schedule `hostname-certificate-renew`, `47 3 * * *`, `ctx.networking.renewHostnameCertificate(job)`) re-issues (not forced; the client's own due rule applies) and re-installs for the four services once `daysRemaining <= ssl.autossl.renew_days`; it is a no-op outside that window, pauses the schedule when the hostname has no AutoSSL certificate, and every issuance enables the schedule again. `GET /api/networking/hostname` carries `renewal: { schedule, cron, enabled, nextRunAt, renewDays }`. | `issueCertificate: false` on an internal `setHostname` call; AutoSSL provider `disabled` (SSL/TLS › Manage AutoSSL) skips the step; the schedule can be paused under Server Configuration › Configure cPanel Cron Jobs. | Service certificates stay self-signed (re-issued for the new name by the `certs` step) until one is installed under Service Configuration › Manage Service SSL Certificates. |
| **The branding images can be embedded from other origins** | helmet sets `Cross-Origin-Resource-Policy: same-origin` on every panel response; `server/src/app.js` overrides it with `cross-origin` for `GET`/`HEAD` under `/api/branding` only, because the landing page (`https://<hostname>/`) and every new account's index page (`http://<domain>/`) embed `https://<hostname>:2087/api/branding/logo`. The route is public, cacheable and carries its own `default-src 'none'` CSP. | None. | — |
| **New sites and the hostname show the branded "Ready to launch" page** | `DEFAULT_TEMPLATES.index` (written into `public_html` at account creation) and `DEFAULT_TEMPLATES.landing` carry the company name, tagline and logo from cPanel › Customization. The seeded admin-side defaults (`WHM` / `WebHost Manager`) are not shown to visitors; the fallback is **Hostingsignal Panel**. A template row that still holds the page migration 012 seeded counts as stock and renders the branded default. | Account Functions › Web Template Editor: save your own HTML (any complete document) or *Reset to default*. Branding: cPanel › Customization. | Your HTML is served instead. |

## Step order of a hostname change

`hostname` → `hosts` → `settings` → `certs` (self-signed service certificates re-issued for the new name) → `dns` → `landing` → `certificate`.
Every step reports `{ step, ok, skipped?, detail?, error?, code?, capability? }`; a failed step never blocks the ones after it, and the hostname is changed whatever happens later.

## Integration notes

- `ctx.web.forceHttps()` is the flag; `ctx.web.landingDocroot` the docroot; `ctx.web.ensureHostnameVhost(req, { hostname? })` never throws; `ctx.web.isServerName(domain)` is the check account/domain creation must apply.
- `ctx.networking.reissueHostnameCertificate({ force }, req)` returns `{ hostname, ip, steps, ok }`; `ctx.networking.renewHostnameCertificate(job)` is the scheduled handler (`{ hostname, skipped, reason? | steps, ok }`).
- `GET /api/networking/hostname` carries `certificate` (the hostname's installed certificate), `landing` (the server vhost row), `renewal` (the schedule) and `capability.ssl` / `capability.web`.
- `templates.save('landing', …)` / `reset('landing')` (Account Functions) return `rendered` from `ctx.web.ensureHostnameVhost`; the editor can show "landing page updated" from it.
- Agent vhost metadata (`# whm-vhost` line) records `redirectHttps`.
